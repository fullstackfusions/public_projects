## 8. The discovery that made the product (21:53–21:55)

Queried CloudTrail through MCP for the agent's events. One agent action shows up at three levels:

1. `aws-mcp.amazonaws.com` · `CallReadWriteTool` · eventType `AwsMcpEvent` · user agent `python-httpx/0.28.1 mcp-proxy-for-aws/1.7.0 claude-code/2.1.280`, with `additionalEventData.downstreamRequests` listing each AWS API and its request ID. Tool arguments: `[HIDDEN_DUE_TO_SECURITY_REASONS]`.
2. The downstream call itself (`sts:GetCallerIdentity`) with `invokedBy: aws-mcp.amazonaws.com` and the matching request ID.
3. Separately, the agent's plain-CLI call, with its own user agent and hermes's IP.

So Chaperone can tell the human, the agent-through-MCP (down to the Claude Code version) and the agent-through-CLI apart, and group every AWS call under the tool call that made it.

- **Video beat:** this is the "aha" chapter. Show the raw JSON, then the tree it becomes.

## 9. Zero to hello-world (02:04:59–02:05:15 UTC)

Two MCP `run_script` calls, 16 seconds of AWS API calls, all by `chaperone-agent` via `aws-mcp`:

| UTC | MCP tool call → downstream AWS calls |
|---|---|
| 02:05:01 | `s3:CreateBucket`, `s3:PutBucketTagging`, `s3:GetPublicAccessBlock`, `s3:PutObject`, `cloudfront:CreateOriginAccessControl` |
| 02:05:15 | `cloudfront:CreateDistributionWithTags`, `s3:PutBucketPolicy` |

- Private bucket `chaperone-web-<acct>-use1` (all public access blocked), OAC, distribution `EDFDVBD6EXAMPLE` (HTTPS only, PriceClass_100, HTTP/2+3), bucket policy scoped to that distribution's ARN. Everything tagged `Project=chaperone`.
- Live at https://d111111abcdef8.cloudfront.net after ~105 s. Direct S3 URL returns 403.
- Surprise: `s3:PutObject` appears **only** inside the MCP event's `downstreamRequests`. It's a data event, which the trail doesn't record, so MCP reveals agent activity the trail alone would miss.
- The page text: "This page was deployed by a coding agent through the AWS MCP Server, and Chaperone recorded it doing so."

## 12. The EventBridge test (03:13 UTC, 30-minute timebox)

- Code folder scaffolded: `infra/`, `backend/`, `mcp/`, `web/`, `design/`, a `.gitignore` that keeps Terraform state, `node_modules`, build output and `.env` out of git, and a README.
- Question: does EventBridge deliver the MCP tool-call events (`AwsMcpEvent`), or only ordinary API events? The whole ingest design depends on it.
- Probe, built by the agent through MCP: SQS queue `chaperone-eb-probe` + EventBridge rule `chaperone-eb-probe` (us-east-1) matching **any** event whose `principalId` ends in `:chaperone-agent`, with state `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS` so read-only events are included. Then one read (`GetBucketTagging`) and one write (`PutBucketTagging`) at 03:13:42.
- Result after 4 minutes (03:18): **6 events arrived, all ordinary `AwsApiCall` events** ("AWS API Call via CloudTrail"), including the read-only `GetBucketTagging`, each with `invokedBy: aws-mcp.amazonaws.com`. **No `AwsMcpEvent`** (`CallReadWriteTool`) arrived, although `LookupEvents` shows both tool-call events in CloudTrail with the matching `principalId`.
- Side notes: `CreateQueue` (03:13:28) matched even though the rule was created a second later, because EventBridge matches when CloudTrail delivers, not when the call happened. The read `sqs:GetQueueAttributes` at 03:13:28 did not arrive; the read-only opt-in may take a moment to apply (unconfirmed).
- Decision D-018: hybrid ingest. Probe rule and queue deleted; the bucket's test tag removed.
- **Video beat:** a 4-minute experiment that changed the architecture. Show the queue's six messages next to the two tool-call events that never came.
